## 1. 定位

一个**整活向**的大型堆料模组：荒诞的压缩层级、夸张的合成门槛、一本正经的科技树，
最终用一件价值连城的东西换回一根木棍。卖点不是平衡，是"坚持"。

- 笑点兑现点：**终极合成 = 附魔一重压缩粗苹果金块 → 木棍**
- 长期目标：**绝对苹果奇点**
- 技术定位：能独立玩（无 AE2 也能跑），装了 AE2 能完整接入存储/合成/自动化

## 5. 数值设计

### 5.1 压缩数学

```
苹果锭 = 1 苹果（1:1 压制，仅统一形状）
N 重压缩 = 9^N 个单位        → 一重 = 9，二重 = 81，…，九重 = 9^9 = 387,420,489
压缩块   = 9 × N 重单位      → 一重块 = 81，…，九重块 = 3,486,784,401
```

数量用 `long` 存储，上限按 9^18 校验（9^19 溢出）。

### 5.2 奇点：硬核（**已定方案 A**）

**定案：绝对苹果奇点 = 九重压缩苹果锭 ×1 = 387,420,489 个苹果。**

选 A 意味着必须接受三件事：

1. 奇点是**图腾级**目标，不是通关条件。"用贵物换木棍"的笑点与之**独立**，几百苹果就能兑现，不受影响。
2. **AE2 档位 2 从"可选"变"必做"**：`ME_STORAGE` + `MEStorage.extract(long)`。否则 3.87 亿要 600 万次 64 格搬运，任何管道都跑不动。
3. 唯一真瓶颈是**苹果产量**（农场），不是机器。压缩机满配后是七十万级/秒的处理动作，喂料跟不上就白搭——
   这也是你装 AE2 的原因：存储与运输能解决，种植不能。

配置兜底保留，默认值按 A 走：

| 配置项 | 默认 | 作用 |
|---|---|---|
| `singularityMode` | `direct` | 改 `shard` 时走离心机碎片折返（省约 30 倍） |
| `applePerTier` | `9` | 每重倍数，可改 3/4/6 给服务器主降档 |
| `maxTier` | `9` | 最大重数，可降到 6 |

服务器主嫌太久可以自己调，**不需要改代码**。

### 5.3 附魔

- 附魔是**数据组件**，不是独立物品：`siao:enchanted`（Boolean）+ `siao:enchant_tier`（int 1..9）
- 名称前缀「附魔」，光效走 `Item#isFoil` 覆写（不额外存 `enchantment_glint_override`，
  免得一个组件两种含义），名字仍是翻译键，JEI/EMI/铁砧/物品栏自动跟着变
- 压缩链规则：
  - 9 个普通 → 1 个普通（上一重）
  - 9 个全附魔 → 1 个附魔（附魔强度原样带上去）
  - 混合输入 → 拒绝（配方不匹配）
- 实现：自定义配方类型 `siao:compression`，在 `assemble(CraftingInput, HolderLookup.Provider)`
  里读输入栈组件决定产物。**四条配方线（压缩 / 拆分 / 装块 / 拆块）全部换成它**，
  因为原版配方类的产物是写死的 `ItemStack`，`getResultItem` 又拿不到输入。
- **为什么不用「普通配方 + `neoforge:components` 附魔配方」的双配方方案**：
  普通配方 `{"item": ...}` 本身就匹配附魔物品（组件默认不参与匹配），
  9 个附魔单位会同时命中两条配方，谁赢由配方表顺序决定 —— 附魔会被普通配方静默吃掉。
  改成单条配方，在 `matches` 里判「9 格附魔状态必须一致」，模糊性从根源消失。
- **附魔不可下泄**：拆分 / 装块 / 拆块用 `"enchant": "reject"`，附魔物品直接不匹配，
  堵掉「1 个附魔拆成 9 个附魔」的复制漏洞；方块不参与附魔。

compressed_{tier}x_raw_{material}          粗形态单位 compressed_1x_raw_iron

只作用于**一重压缩铜锭块**这一阶，向上不扩散（控制 ID 爆炸）。

## 8. 机器与升级（Mek 式）

### 8.1 三台机器

| 机器 | 作用 | 关键接口 |
|---|---|---|
| **苹果压缩机** | 9→1 压缩，支持批量当量；奇点主产线 | `IItemHandler` + `MEStorage` + `ICraftingMachine` + FE |
| **苹果附魔台** | 给压缩单位挂附魔组件，消耗经验/青金石/能量 | `IItemHandler` + FE |
| **苹果离心机** | 解附魔；处理混沌苹果换奇点碎片 | `IItemHandler` + FE |
| **苹果农场** | 1 个树苗 → 8 个苹果，**整个压缩链真正的瓶颈** | `IItemHandler` + FE |

统一基类：`AbstractAppleMachineBlockEntity`
- 能量缓冲 `IEnergyStorage`（FE）
- 升级槽 ×8
- 进度条 + 侧配置（输入/输出/双向）
- 并行处理（受并行升级限制）
- 数据持久化走 `saveAdditional(CompoundTag, HolderLookup.Provider)`

### 8.2 升级体系（基础层 + 进阶层 + 开放注册表）

**关于 "eco"**：查证为 **Neo Eco AE Extension**（Modrinth slug `neoecoae`，作者 DancingSnow0517，1.21.1 NeoForge 可用），
定位是"给 AE2 提供超越原版性能的组件"；另有一个社区附属 `neo-eco-prototype`。
它对我们的意义是**范式**（在原版上限之上再加一层），而不是需要对接的 API ——
我们照这个思路自研，同时把升级类型做成开放注册表，将来任何模组都能挂进来。

**基础层**（8 个升级槽，常规获取）

| 升级 | 效果 | 上限 |
|---|---|---|
| 速度 | 每级处理速度 ×2 | 8 级 |
| 能量 | 每级能耗 ×0.8 | 8 级 |
| 并行 | 每级同时处理 +1 路 | 4 级 |
| 锚定 | 区块卸载继续运行 | 1 级 |

**进阶层**（材料更贵，**突破基础层上限**）

| 升级 | 效果 | 上限 | 获取 |
|---|---|---|---|
| 超频核心 | 速度上限再 +4 级 | 4 | 压缩机 + 奇点碎片 |
| 量子核心 | 能耗上限再 +4 级 | 4 | 附魔台 + 下界合金 |
| 裂变核心 | 并行上限再 +4 | 4 | 离心机 + 混沌苹果副产物 |

- **等级存在数据组件里**，不额外占用 ID
- `UpgradeType` 走 `DeferredRegister` 开放注册表 → 任何模组（含将来装 eco 那类）都能注册自己的升级类型
- 吞吐推演：基础满级（×256）+ 进阶满级（×16）≈ **七十万苹果/秒**的压缩动作；
  此时瓶颈 100% 在农场，不在机器

### 8.3 实现时踩的两个坑（记录，避免重犯）

1. **`ItemStackHandler#insertItem` 会先查 `isItemValid`**
   输出槽的 `isItemValid` 返回 `false`（挡住漏斗和玩家往里塞）会导致**机器自己也塞不进去**，
   表现是「进度条一直在跑，但永远不出货」。内部产出必须用 `setStackInSlot` 绕开校验。
2. **`IEnergyStorage#extractEnergy` 在 `canExtract()==false` 时永远返回 0**
   `EnergyStorage(capacity, receive, maxExtract=0)` 让机器对外「只进不出」是对的，
   但机器自己也就抽不出电来加工了。内部耗能要走自己的 `consume()` 直接改缓冲。

两个坑的症状完全一样（不报错、不断机、进度条空转），只看现象分不出来，必须靠自检用例定位。

## 9. AE2 接入（软依赖，三面全抄）

参考实现就在本地：`_research/Applied-Energistics-2-1.21.1`、`_research/x_appmek/Applied-Mekanistics-dev-1.21.1`（Mek 机器 × AE2 的官方范本）、`_research/x_extae/ExtendedAE`。

> 详细取证见本地报告 [`_research/AE2-1.21.1-第三方机器对接调研.md`](../_research/AE2-1.21.1-第三方机器对接调研.md)（含行号与 URL）。

### 9.1 推料优先级（源码确认）

样板供应器 → 相邻机器是**三级优先**：

| 级别 | 能力 | 推入方式 |
|---|---|---|
| 1 | `AECapabilities.CRAFTING_MACHINE` | `ICraftingMachine#pushPattern(...)`，**整批原子，全有或全无** |
| 2 | `AECapabilities.ME_STORAGE` | `insert(AEKey, long, Actionable)`，**一次推 long** |
| 3 | NeoForge `Capabilities.ItemHandler.BLOCK` | 逐格插入（≤64/次） |

- 三级都是可选加成：**只注册标准 `IItemHandler` 就能被自动化，而且不需要编译期依赖 AE2**
- ⚠️ 注册了 `ME_STORAGE` 会**遮蔽**后面的 `IItemHandler` 路径 → ME_STORAGE 必须是完整正确的存储门面（全 AEKey 类型 + 准确 SIMULATE），否则会吞料
- ⚠️ `Actionable.SIMULATE` 返回 0 会被判"不可用"而永不被选中 → 模拟必须准确
- ⚠️ 供应器会剔除朝向"另一供应器 / 同网络接口"的面

### 9.2 产物回流

- **AE2 不会来机器里取产物**：供应器每 tick 只把自己那 9 格返回槽灌进网络
- 正确做法：机器**主动推回**相邻供应器的返回槽（AE2 用 `registerGenericAdapters` 把它自动适配成普通 `IItemHandler`），或推给未配置槽位的 ME 接口
- 官方 Guide 原话：可以把机器输出管回附近的样板供应器，但不能从它抽

### 9.3 合成面

- `ICraftingMachine` 是 AE2 留给第三方机器的官方口子（铭刻器同款），优先级最高
- 自定义 `IPatternDetails` 的 `IInput.getMultiplier()` 是 **long**，可声明「1 单位 × 9^N」
- 自定义样板必须配 `IPatternDetailsDecoder`，否则合成 CPU 无法持久化
- ⚠️ `getOutputs()` 返回空 list 会 `IndexOutOfBounds`（`getPrimaryOutput()` 默认取 `get(0)`）
- 待实测：超大 multiplier 在合成计划 UI 的显示与计算

### 9.4 随机组件产物的硬限制（混沌苹果）

- 1.21.1 **没有 ad-hoc pattern**；`IPatternProvider` / `IPatternProviderTarget` **这两个类名不存在**（真实名 `PatternProviderTarget`）
- 产物必须在编码样板时写死；`AEItemKey` 身份**包含数据组件** → 随机组件产物与声明 key 不匹配时 `CraftingCpuLogic#insert` 返回 0，**任务永不完成**
- 结论：**混沌苹果不进 AE2 合成链**（与"手动合成/展示物"定位一致）。要进自动化只能自建 `IPatternDetailsDecoder` 并预测输出，不建议

### 9.5 ME 直连（奇点批量）

- `MEStorage#extract(AEKey, long, Actionable, IActionSource)`：long 语义、**无速率限制、无能量成本**，只有重入保护
- 机器作网格节点：`IInWorldGridNodeHost` + `GridHelper#createManagedNode`（`IGridHelper` 在 1.21.1 已不存在）
- 只读快照用 `IStorageService#getCachedInventory()`（每 tick 至多缓存一次）

### 9.6 依赖与构建

| 用途 | 坐标 | 备注 |
|---|---|---|
| 只用 `appeng.api.*` | `org.appliedenergistics:appliedenergistics2:19.2.18:api`（Maven Central，实测可达） | api jar **只含** `appeng/api/**` |
| 要用 `appeng.helpers.*`（`StackWorldBehaviors` 等） | 完整 jar：`maven.modrinth:ae2:19.2.17` / CurseMaven | api jar 里没有 |

- 软依赖写法：`ModList.get().isLoaded("ae2")` + AE2 类型**完全隔离在 compat 类的方法体内** + `mods.toml` 的 `type="OPTIONAL"`；NeoForge 21.1 **没有** `@Mod(condition=...)`

## 10. 贴图管线（构建期生成，不做运行时染色）

素材：`mc-assets/` = **1686 张 256×256 原版物品渲染图**（不是 16×16 贴图，是成品图标级渲染）。

方案：
1. **模板选取**：按形态取基底（锭/宝石/粉/块各自一套）
2. **压缩表现**：把基底按 tier 做「叠层」——N 重就叠 N 层并轻微位移，视觉上自然表达"压了很多层"
3. **附魔表现**：叠加 `enchantment_glint_override`，不额外出图
4. **铜专线**：氧化阶做色相/明度变换（绿→青→暗），涂蜡加高光
5. 输出到 `src/main/resources/assets/siao/textures/item|block/*.png`，256×256

为什么放构建期而不是运行时 `ItemColor`：
- 零 tint 代码，JEI/EMI/光影全部零风险
- 贴图可人工微调，出问题好定位
- 代价：仓库体积（336 张 ≈ 10～15 MB，可接受；必要时降到 128×128）

生成脚本用 Python + Pillow（脚本属于工具，不属于 mod 代码）。

| 物品/方块注册 | `DeferredRegister` 循环 |
| blockstate / model / item model | `BlockStateProvider` + `ItemModelProvider` |
| loot table | `BlockLootSubProvider` |
| 压缩配方（9→1、1→9、块往返） | `RecipeProvider` 循环 |
| 附魔压缩（动态输出） | 自定义配方类 `siao:compression` + 手写 serializer；json 里的 `result` 只是展示产物，真产物在 `assemble` 里算 |
| 铜氧化/涂蜡 | `DataMapProvider` |
| tags | `BlockTagsProvider` / `ItemTagsProvider` |
| lang（中/英） | `LanguageProvider` 循环，名称由模板函数产出 |

配方数量估算：12 材料 × 9 重 × 4 类 ≈ 430 条 + 铜专线 ≈ 60 条 + 机器/杂项 ≈ 30 条。
