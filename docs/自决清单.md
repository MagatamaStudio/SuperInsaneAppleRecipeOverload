## 2. 决定清单

### 2.1 附魔与配方

| # | 决定 | 理由 | 可逆性 |
|---|---|---|---|
| A1 | 四条配方线（压缩/拆分/装块/拆块）**全部**换成自定义类型 `siao:compression` | 原计划只换压缩。但普通配方 `{"item":…}` 会连附魔物品一起匹配，两条配方抢同一批输入，谁赢看配方表顺序 → 附魔会被静默吃掉。只换一条线解决不了歧义 | 🟢 改生成器 + 改一个类，随时退回 vanilla 配方 |
| A2 | 用**单条**配方 + 自定义 `matches` 判「9 格附魔状态一致」，不用 `neoforge:components` 双配方 | 同上，双配方天然有歧义 | 🟢 |
| A3 | 附魔**不可下泄**：拆分/装块/拆块用 `enchant: reject` | 否则「1 个附魔四重 → 9 个附魔三重」是附魔印刷机 | 🟢 改 JSON 一个字段 |
| A4 | 附魔显示走 `Item#getName` 覆写，不塞 `custom_name` 组件 | 组件版会变成斜体、进铁砧会被改成不可翻译的死字符串；覆写版 JEI/EMI/铁砧全部自动跟随 | 🟢 |
| A5 | 光效走 `Item#isFoil` 覆写，不塞 `enchantment_glint_override` | 少一个组件、少一份存档负担 | 🟢 |
| A6 | `siao:enchant_tier` 语义定为「附魔强度 1..9，压缩时原样带上去」 | 设计文档只说了有这个字段，没说数值语义。定为不随压缩增长，避免「压一次涨一级」变成隐性乘法 | 🟢 只影响将来离心机产出系数 |
| A7 | 命名空间前缀用 `prefix.siao.enchanted`（中「附魔」/ 英「Enchanted 」） | 中文无空格、英文有空格，必须分开 | 🟢 |

### 2.2 机器

| # | 决定 | 理由 | 可逆性 |
|---|---|---|---|
| B1 | 三台机器**共用**一个 Block / BlockEntity / Menu / Screen 类，用 `MachineKind` 枚举分支 | 三台的差异只有一个 switch（加工逻辑），其余（FE、升级、存档、GUI、能力）完全一致。三份复制粘贴会让 bug 也复制三份 | 🟡 拆成三个类是一天的机械劳动 |
| B2 | 统一槽位布局：**9 输入 + 3 输出 + 8 升级**，三台一样 | 一套 GUI 底图、一套坐标常量。代价是附魔台/离心机只用得到第 0 个输入格 | 🟢 |
| B3 | 输出槽 `isItemValid = false`（漏斗和玩家都塞不进去） | 防止把机器当箱子用 | 🟢 |
| B4 | 机器对外 `IEnergyStorage` **只进不出**（`maxExtract = 0`） | 机器不是电源。**但这条踩了坑**，见 `设计锁定-v1.md` §8.3 | 🟢 |
| B5 | 压缩机不自己实现压缩规则，直接复用 `SiaoCompressionRecipe#matches/assemble` | 手搓配方和机器用同一套逻辑，才不会出现「手搓能压、机器不能」 | 🟢 |
| B6 | 加一层 `CompressionIndex`（按 RecipeManager 身份缓存的 `Item → 配方` 表） | 直接 `getRecipeFor` 每次过 540 条配方 ≈ 4900 次比较，满配机器一 tick 十几次，几十台就拖垮服务端 | 🟢 |
| B7 | 锚定升级用 `ServerLevel#setChunkForced` | NeoForge 的 ticket 系统在这个版本 API 变动大；强加载区块语义直观、够用 | 🟢 |
| B8 | 机器方块**不加 FACING**（六面同贴图） | 朝向目前没有任何作用（侧配置还没做），加了只是多两个 bug 来源 | 🟡 加回来要改 blockstate + 模型 |
| B9 | 删方块时把内容物 `popResource` 掉地 | 否则拆机器吞东西 | 🟢 |
| B10 | 补全 **138 个方块的战利品表** | 这是阶段 1 就存在的老 bug：没有 loot table，挖什么方块都**什么都不掉**。跟机器无关，顺手修了 | 🟢 |

### 2.3 升级

| # | 决定 | 理由 | 可逆性 |
|---|---|---|---|
| C1 | 升级等级 = 槽内**数量 × 单件等级**，累加后按类型夹上限 | 8 个槽 × 64 个/槽也够表达高等级，同时保留「等级存数据组件」的设计意图 | 🟢 |
| C2 | 能耗公式 `0.8^等级`，下限 5% | 设计写「每级 ×0.8」，没说下限；不设下限会归零 | 🟢 |
| C3 | 进阶层上限叠加方式：速度 8+4=12、能量 8+4=12、并行 4+4=8 | 设计写「上限再 +4」 | 🟢 |
| C4 | ⚠️ `UpgradeKind` 用 **enum**，不是设计文档写的「开放注册表」 | 真注册表要 `NewRegistryEvent` + `RegistryBuilder`，这个版本里我无法在本地验证（你要求不跑本地服务端），而 enum 序列化用的是 **id 字符串**不是序数，将来换成真注册表**不破坏存档** | 🟡 见第 3 节 |

### 2.4 构建与 CI

| # | 决定 | 理由 | 可逆性 |
|---|---|---|---|
| D1 | 加 `.github/workflows/build.yml`，**两个 job** | 你要求「交给 CI 编译」。但我坚持加第二个 job 真跑服务端：`build` 从第 2 轮起就一直绿，而期间有 3 个「机器完全不出货」级别的 bug 它一个都发现不了 | 🟢 删掉 selftest job 即可 |
| D2 | 自检日志额外输出一行纯 ASCII `RESULT pass=N fail=0`，CI grep 它 | 日志文件是本机代码页（GBK）写的，CI 上拿中文 grep 会假阴性（我自己就踩过） | 🟢 |
| D3 | `settings.gradle` 的离线插件仓库检查改成**只在 `--offline` 时**强制 | 否则 CI 直接死在配置阶段 | 🟢 |
| D4 | 加 `.gitattributes`，锁 `gradlew` 为 LF | Linux runner 上 shebang 带 `\r` 会 `bad interpreter` | 🟢 |
| D5 | CI 里先 `chmod +x gradlew` | Windows 提交的文件没有可执行位 | 🟢 |
| D6 | 做了**第一个 commit** 并推到 `origin/main` | 仓库此前零提交，CI 无从谈起。分支 `main`，作者用你本机已配置的 `KujouShiori <651715794@qq.com>` | 🟢 仓库是你的，随时 reset |

## 3. ⚠️ 和你《设计锁定 v1》不一致的地方（**请复核**）

这四条是我自己拿的主意，其中三条影响玩法手感：

| 编号 | 设计文档原文 | 我实际做的 | 为什么 | 反悔成本 |
|---|---|---|---|---|
| **X1** | §8.2「`UpgradeType` 走 `DeferredRegister` 开放注册表 → 任何模组都能注册自己的升级类型」 | 用 enum，序列化按 id 字符串 | 真注册表在这个版本要额外接 `NewRegistryEvent`，我无法本地验证；而 enum 的 id 字符串序列化保证将来替换不掉存档 | 半天，且不破坏存档 |
| **X2** | §8.1 附魔台「消耗经验/青金石/能量」 | 只消耗 FE，不消耗经验和青金石 | 机器里扣玩家经验要处理「经验归属」（谁的？离线？），是独立设计问题；青金石要再加一个催化剂槽，而三台机器现在是统一槽位布局 | 一天，需要重新设计 GUI |
| **X3** | §12 阶段 6 才有「奇点碎片」 | 阶段 3 就引入了 `siao:singularity_shard` 物品 | 离心机的设计产出就是碎片，不然这台机器没有产物 | 零，删物品即可 |
| **X4** | §8.1「进度条 + 侧配置（输入/输出/双向）」 | **侧配置没做** | 侧配置要接 `FACING` + 每面配置持久化 + 额外 GUI，是独立一块。当前所有面都是双向 | 一天 |

另外两条顺手改了但你应该不会反对：

- **X5**：§8.1 说三台机器各自 `IItemHandler` + FE，我额外给了 `EnergyStorage` 能力（管道能灌电），否则机器只能靠玩家手投电。
- **X6**：升级物品的「等级存数据组件」我实现了（`siao:upgrade_level`），但机器累加时同时乘了**堆叠数量**，所以 8 个槽各放 1 个 1 级速度升级 = 8 级，和 Mek 手感一致。

## 4. 我动了仓库以外的东西

| 位置 | 改动 | 为什么 | 怎么撤销 |
|---|---|---|---|
| `~/.gradle/gradle.properties` | **追加**了一行 `org.gradle.java.installations.paths=…` | 这行原本在项目 `gradle.properties` 里，但 CI 的 Linux runner 会把 `C:\Program Files\…` 当 URI 解析而崩。挪到用户级后本地构建照旧、CI 不受影响 | 删掉那行（文件末尾，带中文注释），同时按 `docs/BUILDING.md` 的说明处理 |

**没有动**：你的代理配置、`C:\Program Files` 下的任何东西、PCL 启动器目录、其他任何仓库。

### 7.2 关于「GUI 直接抄 AE2 和 MEK」

你提了之后我去读了本地 AE2 源码里的**真实布局定义**，不是凭印象：

- `assets/ae2/screens/inscriber.json` → 机器界面 **176×178**，标题在 `(8, 6)`，玩家背包 `bottom: 84`，快捷栏 `bottom: 26`
- `assets/ae2/screens/common/player_inventory.json` → 玩家背包 `left: 8, bottom: 84, BREAK_AFTER_9COLS`

结论：**我的布局其实已经和 AE2 同一套基准**。
我的是 176×200，玩家背包 top = 200−84 = **116**、快捷栏 = 200−26 = **174** —— 正好就是 AE2 那套「底对齐 84 / 26」算出来的值。

| # | 决定 | 理由 |
|---|---|---|
| X10 | **保持 176×200，不改成 176×178** | 差的这 22px 正好是 8 个升级槽那一行。AE2 的做法是把升级槽藏在右侧「工具箱」标签页后面（`common.json` 的 `upgrades: right 2, top 0`），Mek 也是单独的升级标签页。**我无法用眼睛验证一个可折叠标签页渲染正常**，所以选择平铺。等你进游戏看过，想改成标签页我再改 |
| X11 | **不抄 AE2 的贴图**，只抄几何数字 | AE2 是 LGPL-2.1，我们是 MIT。把 `guis/inscriber.png` 拷进仓库会有许可问题。只借「176 宽 / 18px 槽 / 标题 8,6 / 底对齐」这些几何约定，贴图继续自己生成 |
